# ADR 0012: Integración con ERP (post-MVP)

## Estado

Aceptado

## Contexto

El PRD supone "el ERP de la botica cuenta con infraestructura para soportar consultas en línea y
decrementos de stock concurrentes" (§7) y define un módulo de contingencia manual para caídas de la
API del ERP (RF-05). Sin embargo, no existe un contrato/API del ERP definido ni disponibilidad
garantizada para el MVP.

## Decisión

Dejar la **integración con el ERP central post-MVP**. En el MVP, el **módulo de stock manual**
(RF-05) es la fuente de verdad del inventario.

### Contrato de la interfaz de inventario enchufable (W-02)

Para garantizar atomicidad transaccional durante el checkout y permitir que un pedido con múltiples
ítems se reserve o deduzca como una unidad indivisible (evitando inconsistencias parciales), la capa
de dominio interactúa a través de `InventoryProviderProtocol` con soporte de lotes y contexto transaccional:

```python
from dataclasses import dataclass
from typing import Protocol, Any

@dataclass(frozen=True)
class StockItemOperation:
    product_id: int
    quantity: int

class InventoryProviderProtocol(Protocol):
    async def get_available_stock(self, product_id: int) -> int: ...
    
    async def reserve_stock_batch(
        self, items: list[StockItemOperation], session_id: str, ttl_seconds: int
    ) -> bool: ...
    
    async def release_reservation_batch(
        self, items: list[StockItemOperation], session_id: str
    ) -> None: ...
    
    async def confirm_deduction_batch(
        self, items: list[StockItemOperation], session_id: str, tx_context: Any = None
    ) -> bool: ...
    
    async def update_manual_stock(
        self, product_id: int, new_quantity: int, updated_by_user_id: int
    ) -> None: ...
```

En el MVP, la implementación inyectada por defecto es `LocalMySQLInventoryProvider`. Durante la
Fase 2 del Checkout (ADR 0013), `confirm_deduction_batch` recibe la sesión activa de base de datos
(`AsyncSession` como `tx_context`) para que la deducción de existencias se ejecute dentro del mismo
`COMMIT` de MySQL que crea el `Pedido` y el `Pago`. Cuando el conector del ERP esté disponible,
`ERPIntegratedInventoryProvider` implementará este mismo contrato enviando la transacción en bloque.

## Alternativas consideradas

- **ERP en el MVP con circuit breaker + fallback** — cumple el supuesto literal del PRD, pero
  depende de una API de ERP hoy inexistente (contrato y disponibilidad no definidos), arriesgando el
  lanzamiento.

## Consecuencias

- Salida a producción sin depender de un tercero no disponible.
- Trade-off: no hay sincronización automática con el ERP en el MVP; el stock manual puede divergir
  del ERP real hasta que se implemente la integración.
