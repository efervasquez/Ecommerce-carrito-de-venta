# ADR 0015: Cumplimiento LPDP (minimización + cifrado)

## Estado

Aceptado

## Contexto

El PRD RNF-02 exige cifrado SSL/TLS y cumplimiento estricto de la Ley de Protección de Datos
Personales (LPDP) de Perú al procesar recetas médicas (dato de salud) e historiales de compra.
`AGENTS.md` §6/§8 refuerza: secretos por variables de entorno, sin loguear datos sensibles, red
aislada.

## Decisión

Aplicar **minimización + cifrado en tres capas**:

### 1. TLS en tránsito

TLS 1.2+ obligatorio en IIS para todas las comunicaciones cliente ↔ servidor. Certificado
gestionado vía Let's Encrypt o certificado comercial instalado en IIS.

### 2. Cifrado en reposo: InnoDB TDE (ampliado tras revisión adversarial W-07)

Usar **Transparent Data Encryption (TDE) de InnoDB** para cifrar todos los tablespaces de MySQL
en disco:

- **Mecanismo**: InnoDB tablespace encryption (`ALTER TABLE ... ENCRYPTION='Y'`) sobre todas las
  tablas que contengan datos personales (`Usuario`, `Pedido`, `Pago`, `Carrito`, `Receta`,
  `Reclamo`, `tokens`).
- **Keyring**: archivo `keyring_file` almacenado **fuera de la raíz web de IIS** y del directorio
  de datos de MySQL, en una ruta protegida del sistema (ej.
  `C:\ProgramData\MySQL\keyring\keyring_encrypted`), con permisos restringidos al usuario de
  servicio de MySQL.
- **Ventaja**: transparente para la aplicación. Queries normales (`WHERE email = ?`), índices y
  búsquedas funcionan sin cambios. Protege contra robo del disco físico, copia no autorizada de
  archivos `.ibd` y filtración de backups sin descifrar.
- **Limitación conocida**: no protege contra un atacante que obtenga acceso al proceso MySQL en
  ejecución (porque MySQL descifra en memoria para operar). Para el perfil de amenaza de un
  servidor on-premise en red interna con firewall, este nivel es suficiente para el MVP.

### 3. Minimización de PII y retención

- Solo se almacena el email y los datos estrictamente necesarios para el flujo de compra.
- La **receta médica** (dato de salud) se trata con **retención mínima**: el documento original
  (foto/PDF) se elimina tras el procesamiento OCR exitoso, conservando solo el resultado
  estructurado (componentes y cantidades extraídos). El plazo exacto de retención del resultado
  queda por definir con BA/PM según la regulación LPDP peruana aplicable.
- Sin loguear contraseñas, tarjetas ni datos de salud (ya lo exige `AGENTS.md`).

## Alternativas consideradas

- **Solo TLS en tránsito, sin cifrado en reposo** — menos trabajo, pero riesgo de incumplir LPDP
  ante una filtración de la base de datos (robo de disco, backup expuesto).
- **Cifrado a nivel de aplicación (AES-256 por columna)** — más granular, protege incluso si el
  atacante accede al proceso MySQL. Descartado porque rompe queries sobre columnas cifradas (no
  se puede hacer `WHERE email = ?` con cifrado no determinístico sin un hash auxiliar), añade
  complejidad significativa y es desproporcionado para el perfil de amenaza del MVP.

## Consecuencias

- Cumplimiento LPDP con cifrado en reposo verificable y retención mínima de datos de salud.
- Trade-off: gestión del keyring file (respaldo, protección, rotación eventual) y definición de
  plazos legales de retención con el BA/PM. El TDE de InnoDB requiere MySQL Enterprise o
  Percona Server (que incluye TDE en su edición gratuita); verificar compatibilidad con la
  versión de MySQL instalada.
